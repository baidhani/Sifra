- [x] STORY-012: share a credential securely
  - Date: 2026-09-10
  - Session: CC-20260909-a1k4
  - What changed: Added `Sifra.Vault.Sharing` (`SharedCredentialService`, `ShareRegistryStore`, `ShareRecord`). Flagged and confirmed with the user before building: this app has no multi-user/account system, so "recipient" is modeled as another local `SharedCredentialService` instance (another device or Sifra install) rather than a new account layer. `CreateShare` re-encrypts a credential under a key derived from a passphrase the recipient is told out of band (never stored or transmitted by this service); `AcceptShare` is the recipient-side operation and is also the revocation checkpoint — it checks the registry's `Revoked` flag before decrypting, the same idiom as device revocation (STORY-009). `RevokeShare` is idempotent.   - Verification: `dotnet test` — 144/144 passed. Live-verified via a throwaway script exercising the exact CLI-section code against a real temp vault: share created → accepted with the correct passphrase → wrong passphrase correctly refused → revoked → post-revocation access correctly refused, with the resulting `share-registry.json` and `operations.log` inspected directly and confirmed to contain no plaintext (secrets only ever present as AES-GCM ciphertext; log lines carry only share id, recipient label, and outcome).   - Notes: **Documented limitation, stated plainly rather than implied away** — revocation cuts off the app's own access path going forward; it cannot un-share plaintext a recipient may have already copied elsewhere before revocation.
